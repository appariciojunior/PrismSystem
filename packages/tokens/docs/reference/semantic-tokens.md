## Core Principle: 1:1 Semantic Token Mapping Across All Themes

**All semantic tokens are structurally and semantically identical across all themes.** For any given semantic token (e.g., `messaging.fill.warning`), the meaning and usage are identical whether you are in the `light/ core`, `light/ comment`, `dark/ core`, `dark/ comment`, or any other theme.

**Do not select between themes for semantic tokens.** Always use the canonical semantic token path without theme qualification.


This design ensures:

- Consistent semantic meaning across all product surfaces
- Simpler component APIs (one token, not 14 variants)
- Reliable Figma Variables export (strict structural parity)
- Theme switching without semantic confusion

## Static Color Tokens

Static color tokens maintain consistent colors regardless of light/dark mode by using mode-specific ramp references. These tokens are useful for elements that must have guaranteed fixed colors independent of the theme's mode.

### Available Static Color Tokens

| Token                  | Light Mode Reference | Dark Mode Reference | Always Resolves To |
| ---------------------- | -------------------- | ------------------- | ------------------ |
| `surface.static.dark`  | `neutral.1000`       | `neutral.50`        | `#000000` (black)  |
| `surface.static.light` | `neutral.50`         | `neutral.1000`      | `#ffffff` (white)  |
| `text.static.dark`     | `neutral.1000`       | `neutral.50`        | `#000000` (black)  |
| `text.static.light`    | `neutral.50`         | `neutral.1000`      | `#ffffff` (white)  |
| `border.static.dark`   | `neutral.1000`       | `neutral.50`        | `#000000` (black)  |
| `border.static.light`  | `neutral.50`         | `neutral.1000`      | `#ffffff` (white)  |

### How Static Tokens Work

Static tokens use **mode-specific ramp references** to achieve **mode-independent colors**. This is the opposite of normal semantic tokens which use the same ramp step in both modes (producing different colors).

**Example**: `surface.static.dark`

- In light mode: references `neutral.1000` → resolves to `#000000` (black)
- In dark mode: references `neutral.50` → resolves to `#000000` (still black!)

The ramp steps are different per mode because the neutral ramp is reversed in dark mode:

- Light mode: `neutral.50` = white, `neutral.1000` = black
- Dark mode: `neutral.50` = black, `neutral.1000` = white (REVERSED!)

### When to Use Static Tokens

Use static tokens when:

- **QR codes / Barcodes**: Must be pure black/white for scanning reliability
- **Branded assets**: Brand guidelines require fixed colors across all modes
- **Compliance elements**: Legal or regulatory elements with mandated appearance
- **Accessibility overlays**: High-contrast overlays that need guaranteed fixed colors
- **Watermarks / Logos**: Brand elements requiring consistent color independent of theme

### When NOT to Use Static Tokens

Use normal semantic tokens (e.g., `text.primary`, `surface.canvas`) when:

- Element should adapt to light/dark mode (most UI elements)
- Following standard theming patterns
- Providing consistent user experience across different modes
- Colors should inherit from theme changes

### Code Examples

**HTML/CSS**:

```html
<!-- Fixed black QR code background -->
<div class="qr-container" style="background-color: var(--surface-static-dark)">
  <svg><!-- QR code --></svg>
</div>

<!-- Fixed white text overlay -->
<div class="watermark" style="color: var(--text-static-light)">
  © Design System
</div>
```

**React**:

```tsx
import { tokens } from '@ds/tokens';

export function QRCode() {
  return (
    <div style={{ backgroundColor: tokens.surface.static.dark }}>
      {/* QR code content */}
    </div>
  );
}
```

### Description Writing Guidelines

Token descriptions must maintain semantic abstraction without referencing specific colors, hex values, or implementation details.

**Core Principles:**

1. **Semantic Purpose First**: Describe what the token does, not what it looks like
2. **Theme-Agnostic**: Descriptions must work for both light and dark modes
3. **Implementation-Independent**: Avoid referencing specific color steps or palette names
4. **Concise & Clear**: 1-2 sentences maximum, focus on essential information
5. **Consistent Structure**: Follow established patterns within token groups

**Avoid (❌):**

- Specific color names: "white", "black", "red", "blue"
- Color codes: "#FFFFFF", "neutral.50", "error.800"
- Implementation details: "Error color", "uses brand blue"
- Prescriptive UI patterns: "displayed in confirmation modals", "only for sidebars"

**Use (✅):**

- Semantic purpose: "signals danger", "indicates active state", "provides emphasis"
- Hierarchy description: "high-emphasis", "medium-emphasis", "subtle", "prominent"
- Functional context: "for interactive elements", "in form inputs", "on elevated surfaces"
- Interaction behavior: "on hover", "during pressed state", "when focused"

**Example Patterns:**

| Token Type     | Good Description                                                                                    | Bad Description                                                |
| -------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Fill (default) | "Background for primary action buttons. High-emphasis visual treatment for most important actions." | "Blue background for primary buttons. Uses brand.blue.700."    |
| Fill (hover)   | "Background hover state for primary actions. Provides visual feedback during interaction."          | "Darker blue on hover. 10% darken modifier applied."           |
| Text           | "Text for destructive actions. High contrast ensures readability and signals danger."               | "Red text color (error.800) on white background for WCAG AAA." |
| Border         | "Border for form inputs. Defines boundaries and indicates interactive areas."                       | "1px solid neutral.300 border for text fields."                |

**State Token Patterns:**

- **Default**: Describe base purpose and emphasis level
- **Hover**: Focus on providing visual feedback during interaction
- **Pressed**: Emphasize completion of interaction or confirmation
- **Disabled**: Explain reduced emphasis and non-interactive state

**Typography Token Patterns:**

Typography tokens include a soft HTML element hint to guide correct semantic markup. Add the hint at the end of the description, after a full stop.

- **Heading tokens**: "… Typically h1.", "… Typically h2, h3."
- **Body / paragraph**: "… Use p."
- **Inline links**: "… Use a inside p."
- **Standalone links**: "… Use a."
- **Captions**: "… Use figcaption or span."
- **Buttons**: "… Use span inside button."
- **Labels**: "… Use label or span."
- **Display / decorative**: "… Decorative brand use only. Use p or span."

HTML hints are descriptive, not prescriptive. They reflect the most common semantic usage, not a hard contract.
