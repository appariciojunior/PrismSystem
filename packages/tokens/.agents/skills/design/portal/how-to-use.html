How to use the skills.

A practical guide for designers, design engineers, PMs and QA. Set up the Figma connection once, learn what skills and agents are, then use them day to day. Aim: be productive in fifteen minutes.

Step 00What you're looking at

A set of helpers built into your editor that bridge Figma and the design system. You use them by typing natural sentences. They produce Markdown reports.

The portal has three kinds of thing in it, and they relate like this:

The building block

Skill

A focused file that does one job. Twelve of these. Examples: token-mapping-audit finds every value in a Figma frame and maps it to a token. a11y-check runs an accessibility audit on a frame.

You can call a skill on its own when you want surgical control over one specific check.

The entry point

Agent

A bundle that calls multiple skills in the right order for a real job. Four of these. Examples: handoff-agent runs eight or nine skills to turn a design into an engineering packet. critique-agent runs four checks in parallel.

Most days, you call agents. Skills are the plumbing underneath.

And underneath everything sits one foundation file, the design-dna, which captures who your brand is, the eleven channels, the token architecture, voice rules, motion philosophy. Every agent loads it before doing anything else, so every output is grounded in how we design.

Step 01Set up the Figma connection

One-time setup per machine. Takes about ten minutes. After this, every skill that touches Figma will work.

The skills talk to Figma through two Model Context Protocol (MCP) servers, plus a third for the design tokens. You install once, configure once, and after that they boot up with your editor automatically.

Before you start

You need: Figma Desktop installed, Node.js 18 or newer, a Figma personal access token, and your editor (VS Code, Cursor, Codex or similar) opened on the ds repo.

  1. Install the Figma Desktop app. If you don't have it, get it from figma.com. The setup needs the desktop app, not just the browser.
  2. Get a Figma personal access token. In Figma desktop, open Settings, scroll to Personal access tokens, generate one with read access (or read + write if you'll be running the build agent later). Copy the token — it starts with figd_.
  3. Create the env file. In your home directory, make a file called .figma-console-mcp.env and paste in: 
    FIGMA_ACCESS_TOKEN=figd_xxx
    Replace figd_xxx with your real token. Note: it's FIGMA_ACCESS_TOKEN, not FIGMA_API_KEY.
  4. Enable Desktop MCP Server in Figma. Open any Figma file, switch to Dev Mode (top right), open Preferences, and turn on Desktop MCP Server. You'll see the indicator light up.
  5. Open the repo in your editor. The repo includes .vscode/mcp.json with the right MCP server configuration baked in, so when you open the project the servers boot automatically. Three of them: figma-console, figma-desktop, and ds-tokens-mcp.
  6. Verify it works. Open the AI panel in your editor (Claude, Cursor, Copilot Chat, etc.) and ask: "Check Figma status." You should get back a status report showing the MCPs are connected.

The one rule you'll hit every time

Whenever an agent is about to touch a Figma URL, it will ask: "Is the Figma Desktop Bridge plugin currently running in that file?" Answer honestly — if it isn't, open Figma, open the file, run the Desktop Bridge plugin, then tell the agent to continue. This gate is mandatory and exists to stop the agent guessing about file state.

That's the whole setup. Future sessions need only the env file to be present and Figma Desktop to be running.

Step 02Skills, agents and the DNA

A two-minute mental model. Stick this in the back of your head and the rest makes sense.

Three layers, top to bottom.

The agents are what you call.

Four of them. They're how you actually talk to the system. Each agent owns a moment in the design lifecycle:

  • prototyping-agent — early. You're exploring an idea, want a sanity-check on tokens or motion, want to think out loud.
  • critique-agent — middle. You have something on the page and want to know if it's any good before showing it to engineering.
  • handoff-agent — late. The design is done. Produce the engineering packet.
  • build-agent — after handoff. You're the design engineer scaffolding the component.

The skills are the plumbing.

Twelve files. Each does one specific job. You usually don't call them directly. They run inside agents. But you can call one on its own if you want a single check (e.g., just run a11y-check, skip the rest).

The DNA is the ground truth.

One file: design-dna. The brand, the eleven channels, the token architecture, the voice rules, the motion philosophy, the anti-patterns. Every agent loads it as a preamble before doing its work. That's why an output from critique-agent sounds like your brand and not like a generic design review.

If you remember one thing

Call agents, not skills. Skills exist; you can read them; but agents are designed for the way you actually work. The portal index page shows the four agents at the top for that reason.

Step 03Using them day to day

You type a natural sentence in Claude, Cursor, Copilot or whichever AI tool you've got open. The system picks the right agent or skill and runs it.

No special syntax. No magic commands. You can name the agent if you want exactness, or you can just describe what you want.

Example 1: thinking out loud

I'm prototyping a callout card for the Comment section. What surface token should I use?
Loads the DNA… For Comment, the channel-aware surface is light/ comment/ surface/ primary for the card body, with light/ comment/ text/ primary for the heading. If the callout is opinionated, light/ comment/ accent/ primary on the left border works. Don't reach for product.channel.comment directly — let the channel scope at section level do the work.

Example 2: critiquing

Critique the design at https://figma.com/design/abc123?node-id=42-1024
Mandatory gate: Is the Figma Desktop Bridge plugin currently running in that file? (You answer yes.) Running design-critique, a11y-check, content-style-check in parallel… done. 2 errors, 9 warnings. Top three fixes: contrast on the secondary button label (3.9 needs 4.5), em dash in the headline, three off-scale spacing values (13px, 18px, 22px). Full report at .design/comments-modal/CRITIQUE_REPORT.md.

Example 3: full handoff

Hand off the comments-modal feature, Figma light at <url>, dark at <url>, channel comment, ticket COM-412
Loading DNA. Running preflight. Bridge running? (yes) Running token audit on light frame… 23 tokens captured, 21 semantic, 2 unmapped. Pause: do you want to fix those before I continue, or flag them in the packet? (continue) … Final output: .design/comments-modal/PACKET.md plus the full feature folder. Attach to COM-412.

All three examples follow the same pattern: you describe what you want, the agent loads the DNA, runs the right skills, pauses when something needs your input, produces a report.

Step 04Reading the outputs

Every output is a Markdown file in a predictable place. Open it in VS Code or any Markdown viewer.

The portal's Skills section lists every file each skill produces. The shape:

  • Each feature you work on gets a folder: .design/<feature-name>/. Created automatically the first time you run anything against it.
  • Inside, files are predictable: SPEC.md for the developer spec, TOKEN_AUDIT_LIGHT.md for the token audit, CRITIQUE_REPORT.md for critique findings, A11Y_CHECK.md for accessibility, and so on.
  • The final artefact you attach to an engineering ticket is always PACKET.md.
  • Each report has a Summary table at the top — read that first. The detail is below if you want to dig in.
  • Every report ends with a Provenance section: which Figma node it was run against, the tokens snapshot SHA, the skill version. That's your audit trail.

What outputs are not

Reports are evidence, not verdicts. If a finding doesn't make sense in your context, push back. The skills are direct on purpose — they say "contrast 3.9 vs threshold 4.5" rather than "the contrast might be a bit low" — but they're not infallible. Your judgement still matters.

Step 05Troubleshooting

The common things that go wrong, and how to fix them.

"The agent says Desktop Bridge isn't running"

Open Figma Desktop, open the file the URL points to, then run the Desktop Bridge plugin from the Plugins menu. Once the indicator confirms it's running, tell the agent "yes, continue".

"It says the Figma URL can't be fetched"

Usually means the env file is missing or the token is wrong. Check ~/.figma-console-mcp.env exists and contains a valid FIGMA_ACCESS_TOKEN. Then restart your editor so the MCP server picks up the env.

"Token MCP returns nothing"

Means the Design System Tokens MCP server isn't running. Check that the workspace .vscode/mcp.json is loaded. Restart your editor. If it still doesn't work, ask in the design-systems channel.

"It produced a report but a column is empty"

Open the report, scroll to the Provenance section at the bottom. If it says "Token MCP cache stale" or "extraction returned partial", re-run the same skill with the same input. The retry sequence is designed to recover from these.

"I asked for a critique and got code"

The wrong agent picked up the request. Be explicit: name the agent ("Use critique-agent to…"). Or rephrase to be unambiguous. The agents have polite redirects when they detect a mismatch, but they can't always tell.

Step 06Where to go next

Pick the right starting point for your role and go.

  • If you're a designer: open the Agents section on the main page, click the prototyping-agent card, copy one of its example prompts, try it on a Figma frame you know.
  • If you're a design engineer: read the Design DNA first (it's the foundation), then try the build-agent on your next component.
  • If you're a PM or content reviewer: ask a designer to share their next PACKET.md. Notice you don't need Figma to understand it.
  • If you're QA: try the visual-vs-built check on a component that just landed in Storybook. It surfaces the gaps between design and implementation.

Download the full guide or proposal if you want the longer reads. They cover the same ground in more depth, plus the rationale for why the system is shaped this way.

One last thing

The system gets better the more it's used. Every report feeds the monthly audit, which surfaces system-level patterns, which improve the rules, which improve the next report. If something feels wrong or generic, raise it in the design-systems channel. The DNA is a living file.
